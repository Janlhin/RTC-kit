## 零、先看这张画（给不熟悉这套东西的人）

小区里有三个角色：



* **钟表**（`code/rtc.py`）= 装在配电房，每 5 分钟看一次时间。到点拉铃；不会累、不会走神、不会记错。

  今天响了几次、谁按了「停了」，它记在一本**打卡本**（`state/alarms.json`）。**只有它能写这本。**

* **物业**（模型）= 只在业主打电话过来时才接。会说话、会办事，但**它没进过配电房**，所以不知道今天几点打铃。

* **业主**（用户）= 写一张**排班表**（`rules/routines.json`），说几点打铃。

于是有那个经典场景：业主问「我下午几点有安排？」物业说「我不知道，你告诉我吧。」

不是偷懒 ——**排班表锁在配电房里，它手上没有。**

补法就是**在物业桌上钉一张纸**，钟表每次拉完铃 / 改完时间就重新抄一遍贴上去。

那张纸 = `AGENTS.md` 的自动区块；物业懒得抬头时还可以**打电话问钟表**（`rtc.py brief`）。

## 一、这个项目是什么形态

**规则包（rule pack）+ 一个可选参考实现**，不是独立软件。



* 分发单元是 `SKILL.md` + Markdown 规则 + JSON Schema + 一份可选参考实现 `code/rtc.py`。

* 宿主负责会话、上下文注入、渠道投递与调度（当前参考宿主：Hermes Agent）。

* 规则包本身不常驻、不监听端口、不管理账号。

这样设计的目的：**规则能被未来的软件直接读走**，不绑定任何运行时。

## 二、三层 + 一个调度者



```
┌─────────────────────────────────────────────────────────┐
│ ① 表达层（模型）                                         │
│   用户说人话 → 翻译成命令；命令结果 → 说回人话            │
│   不判断「该不该响」，不直接读写状态                       │
└──────────────────┬──────────────────────────────────────┘
                   │ 只有一条线：命令行 + 退出码
┌──────────────────▼──────────────────────────────────────┐
│ ② 判断层（code/rtc.py）                                  │
│   plan / due / ack / check / postpone / cancel /         │
│   complete / disable / enable / set-time /               │
│   schedule / history / status / metrics / brief          │
│   纯布尔逻辑，不调模型；**唯一写状态的地方**              │
└──────────────────┬──────────────────────────────────────┘
                   │ 读配置 / 写状态 / 写快照
┌──────────────────▼──────────────────────────────────────┐
│ ③ 内容层（文件）                                         │
│   rules/routines.json   时刻表（人写）                   │
│   state/alarms.json     今天的账本（只有代码写）          │
│   state/alarms.next.json 次日预排账本（06:00 plan 写）    │
│   state/history.db      执行历史（四表，唯一真相源）      │
│   state/schedule/*.json 每日快照（代码写，人读的派生副本）│
│   state/metrics.db      统计索引（旁路，可缺失）          │
│   state/events.json     L2 事件影子账本（P1 派生；P2 起 .ics 为准）│
│   tasks.md / errors.md  人的东西                          │
└─────────────────────────────────────────────────────────┘

④ 宿主调度（cron）= 每 5 分钟叫一次 ②，**不叫 ①**
   rtc-plan  0 6 * * *      每天重建当天时间表，并预排次日账本
   rtc-due   */5 * * * *    判断该不该响，命中就打印文案
```

**① 与 ② 之间只有命令行这一条线**：没有共享内存、没有共享数据库、没有「模型帮忙顺手指一下状态」。

## 三、职责边界（最重要的一张表）



| 事情                                                                         | 归谁                         | 理由                 |
| -------------------------------------------------------------------------- | -------------------------- | ------------------ |
| 判断当前时间是否落在窗口内                                                              | **代码**                     | 纯布尔逻辑，不需要理解力       |
| 状态机 `pending → ringing → delivered / acked / missed / skipped / cancelled` | **代码**                     | 需要确定性、幂等、可审计       |
| 持久化、跨日归档、并发写保护（rev + 文件锁）                                                  | **代码**                     | 事务与唯一约束比提示词可靠      |
| 到点输出什么文案                                                                   | **代码**（`cmd_due` 里的渲染）     | 要措辞，但不需要推理；改文案只改一处 |
| 「今天还剩什么 / 接下来是什么」                                                          | **代码**（`brief`）            | 答案唯一、可回归；模型只负责转述   |
| 把「明天八点叫我」解析成结构化操作                                                          | **模型**                     | 自然语言理解是模型不可替代的部分   |
| 「把上次那个推到下周」需要查上下文                                                          | **模型 + 技能**                | 需要引用关系与常识          |
| 什么能自己办、什么必须问                                                               | **规则**（`auto-resolver.md`） | 人写的边界，不交给模型临场判断    |
| 什么值得打断人                                                                    | **规则**（`priority-map.md`）  | 价值判断属于人            |

一句话：**模型负责理解，规则负责边界，代码负责确定性。**

## 四、为什么把定时从模型手里拿走

早期版本每 5 分钟唤醒一次模型判断「该不该响」。三个问题：



1. **成本**：一天几十次模型调用，只为算一个布尔表达式。

2. **不稳定**：模型可能返回静默标记，导致该响不响且**没有任何报错**。

3. **不可测**：同样的输入不保证同样的输出。

现在：



```
cron（no-agent）
  → rtc.py due          # 确定性判断，零模型调用
  → 命中 → 打印文案      # 宿主投递
  → 未命中 → 不打印      # 宿主把空输出当静默
```

模型只在**用户开口时**被调用：解析请求 → 调用对应子命令。

代价说清：宿主契约是「**stdout = 要投递的正文，空 = 静默；一切诊断走 stderr**」。

任何把诊断信息写到 stdout 的改动，都会变成一条发给用户的垃圾消息。

## 五、单一真相源与派生视图



| 数据        | 唯一位置                             | 谁写                          | 性质             |
| --------- | -------------------------------- | --------------------------- | -------------- |
| 何时响       | `rules/routines.json`            | 人（经 `rtc.py set-time` 等）    | 配置             |
| 今天的账本     | `state/alarms.json`              | **只有** `rtc.py`             | **唯一真相**       |
| 次日预排账本    | `state/alarms.next.json`         | `plan` 06:00 写，跨日 `due` 激活 | 临时槽位，激活后删除      |
| 某天到底怎么排的  | `state/schedule/YYYY-MM-DD.json` | `plan` 写一次，永久               | 权威存档（不可再算出来）   |
| 统计查询      | `state/metrics.db`               | `metrics sync`              | **派生索引，可删可重建** |
| L2 事件影子账本 | `state/events.json`              | `rtc_migrate.py`（离线投影 / P2 迁移后从 `.ics` 重建） | **派生影子副本**；P1 旧 JSON 仍是真相，P2 起 `.ics` 为准、本文件转缓存视图 |
| 给模型看的今日行程 | `AGENTS.md` 的受控区块                | `plan` / `due` / `ack` 自动刷新 | **派生视图，可随时删**  |
| L2 事件台账    | `calendar/<YYYY>.ics`            | 迁移工具 / 后续事件写路径       | **唯一真相（RFC 5545，跨代可读）** |
| 事件 SQL 索引  | `state/calendar-index.db`         | `rtc_calindex.rebuild` 从 `.ics` 灌入 | **派生索引，可删可重建** |

四条硬规则：



1. **派生永不反向写入真相**：`metrics.db`、`AGENTS.md` 区块、任何缓存出问题，`alarms.json` 不受影响，下一次写把它刷回来。

2. **调度状态永不反推任务状态**：`ack` 不勾任务，`missed` 不建任务。

3. **读取时不修复**：发现不一致只记录并告警，禁止静默重建。

4. **规则升级走人工闸门**：同类错误第二次出现才提议改规则，且需人确认。

第 3 条是历史教训：曾有三套自动修复器各自判定对方是错的，互相重建，最终把全部定时任务清空。

**坏文件怎么处理（v2 补充）**：`alarms.json` / `routines.json` 损坏时，代码给一行可读诊断（退出码 `3`、点名文件与行列号），**绝不覆盖原文**，也绝不抛栈退 `1`—— 因为 `rtc-due` 每 5 分钟跑一次，抛栈等于每 5 分钟给宿主留一条看不懂的失败。

**L2 事件台账的真相口径（P2 / D-015）**：

- `calendar/<YYYY>.ics`（RFC 5545 纯文本）是事件台账的**唯一真相**，按 `DTSTART` 年份一年一文件；跨年事件（12/31 起、次日结束）在相邻年份文件各留一段交叉引用。选 `.ics` 而不是 SQLite / 私有 JSON 作真相，是 NFR-2.5 跨代可读（30–40 年）的硬约束：纯文本任何日历软件都能打开，不被 schema 演进绑架。
- `state/calendar-index.db` 只是查询用的**派生只读索引**：整个删掉，`rtc_calindex.rebuild()` 能从零扫描全部 `.ics` 重建；索引查询结果必须与「直接扫 `.ics`」逐条一致（有测试对账）。
- **冲突以 `.ics` 为准**：索引里有、`.ics` 里没有的记录判为陈旧，读取时剔除并往 stderr 留一行可读告警；**不**反向改写 `.ics`（沿用规则 1 与规则 3）。索引损坏只需 rebuild，不触发任何真相修复。
- 迁移期旧 `rules/routines.json` / `state/alarms.json` 留在原地作只读历史，迁移工具不删不改；回滚按备份 manifest 恢复 `.ics` 与索引。
- 影子视图 `state/events.json` 在 `--to-ics --apply` 写完 `.ics`、重建索引后，**由 `.ics` 逐条重建**（写路径动作，不是读取时静默修复），让 P3 适配器读到的核心字段与真相一致；重建幂等、只背契约字段，`.ics` 扩展字段不进派生视图；回滚时影子产物一并按 manifest 恢复或删除。

## 六、产品本体 vs 本地接线（可移植性边界）

这张表决定「哪些东西能被别人装走，哪些只在这台机器上成立」。



| 组件               | 位置                               | 属于产品本体  | 依赖宿主                  |
| ---------------- | -------------------------------- | ------- | --------------------- |
| 判断与状态机           | `code/rtc.py`                    | ✅       | 否（只要 cron 能跑脚本）       |
| 契约与实例            | `contract/*.schema.json`         | ✅       | 否                     |
| 技能（说明书）          | `skills/*/SKILL.md`              | ✅       | 半（要宿主会按需加载技能）         |
| 安装器              | `install.py`                     | ✅       | 半（要按宿主目录布局写）          |
| 回归测试             | `code/tests/*`                   | ✅       | 否                     |
| 实机自检脚本           | `tools/rtc-labtest.py`           | ✅       | 否（实机层用例才是宿主相关）        |
| `AGENTS.md` 自动区块 | 运行时工作区                           | ❌ 本地接线  | 是（要宿主每次会话读 AGENTS.md） |
| `rtc_brief` 插件工具 | `%LOCALAPPDATA%\hermes\plugins\` | ❌ 本地接线  | 是（宿主插件格式）             |
| `v_today` 视图     | `state/metrics.db`               | ⚠️ 可选衍生 | 否（但模型得会写 SQL）         |

判断标准只有一条：**换一台宿主，它还能不能原样成立。** 不能，就写进部署文档，不要进主干。

## 七、新能力该落在哪一层

新增需求时先查这张表，避免又变成一层补丁。



| 需求                 | 落位                                     | 不该落到                     |
| ------------------ | -------------------------------------- | ------------------------ |
| 多一种查询输出（今天、接下来、某天） | ② 的只读子命令（如 `brief`）                    | 不要写进 `AGENTS.md` 让别人解析   |
| 改提醒文案              | ② 的渲染函数                                | 不要在技能里另写一套措辞规则           |
| 多一种状态 / 字段         | ② + `contract/alarm-state.schema.json` | 不要只在技能里口头描述              |
| 让模型更可能知道状态         | ④ 适配（hook / 插件 / 每日推送）                 | 不要靠改 `alarms.json` 塞注释   |
| 宿主专属接线             | 部署文档（+ 可选插件）                           | 不要进 `contract/`、`rules/` |
| 判断边界的调整（什么算打扰）     | `rules/*.md`                           | 不要硬编码进 `rtc.py`          |
| 兼容旧数据的迁移           | ② 的迁移代码，幂等                             | 不要手工改状态文件                |

**验收口径**：任何一层新增的东西，都必须能在 `code/tests/` 里找到一条回归。

## 八、规则如何被软件复用

### 双表示



| 表示               | 位置          | 消费者        |
| ---------------- | ----------- | ---------- |
| JSON Schema + 实例 | `contract/` | 软件、校验器、数据库 |
| Markdown 渲染      | `rules/`    | 人、模型上下文    |

将来写独立软件时：



1. 读 `contract/routine.schema.json` 得到窗口定义

2. 生成自己的调度计划（不依赖任何 agent 平台）

3. 读 `contract/alarm-state.schema.json` 管理状态机

4. 读 `contract/task.schema.json` 渲染任务列表

5. `rules/*.md` 只作为给人看的文档保留

### 规则必须是声明式的

`rules/` 里的文件遵守三条约束：



* **不含路径**：不出现 `C:\...`、`~/.hermes/...`

* **不含平台命令**：不出现具体 CLI、payload 字段、投递渠道名

* **不含个人事实**：所有人名、项目名、时间都用 `{{占位符}}`

违反任一条，规则就重新绑定到某个运行时或某个人，复用价值归零。

（技能层同理：`skills/*/SKILL.md` 里出现硬编码路径，就说明它已经不能移植了。）

## 九、存档策略



```
state/history.db      四张表：windows / daily / checklist / events  ← 历史（唯一真相源）
state/schedule/*.json 每日完整快照，永久                              ← 派生副本（人读、可 diff）
alarms.json           当天计划 + 最近 14 天执行摘要                     ← 主链路当前状态
metrics.db            统计索引，可缺失                                 ← 旁路
```

* `history` / `stats` / `events` 先读 `history.db`；库里没这一天时才退回快照。
  **删掉整个 `state/schedule/` 目录，历史照样查得到**——这是 issue #9 的验收条款 1。

* 库在每次状态写入成功后同步：`plan` / `due` / `ack` / `check` / `postpone` /
  `cancel` / `complete` / `disable` / `enable` 各写自己的行与事件。写库失败只在
  stderr 记一句，绝不阻断提醒本身（审计不参与判定）。

* 老工作区第一次 `plan` 时自动回填：`state/schedule/*.json` 与 `alarms.json`
  里那 14 天摘要都灌进库，历史不会从「装上新版」那天才断。

* 快照仍由 `plan` 写、`fill_snapshot_results` 回填结果，写一次留永久——它现在是
  可以随时重建的副本，不再是唯一的历史存档。

* 删掉「每天重建」省掉了 29 条 Todo + 29 条 Cron，但「每天存档」不能跟着删 —— 那是旧系统 1600 行规则里唯一真正有价值的东西。

## 十、演进路径



```
阶段 1  规则 + 技能 + 一个运行时            ✅ 已完成（v1）
阶段 2  due 判断下沉为代码，cron 零模型调用  ✅ 已完成（rtc.py + 两条 cron）
阶段 3  每日快照 + 统计旁路 + 行程简报        ✅ 已完成（schedule/、metrics.db、brief）
阶段 4  状态迁入 SQLite，四操作由代码提供     ⏳ 部分（metrics.db 只是旁路索引）
阶段 5  独立软件：直接消费 contract/ 下的 schema（规则原样复用）
```

每个阶段都不改 `rules/` 和 `contract/` 的字段定义 —— 这是「复用规则」的实际含义。

## 附：一个提醒的完整生命周期（照着这条线排查）



```
人改时刻表 (set-time / 手改 routines.json)
   → plan（每天 06:00 或 --force）      生成当天窗口，写快照
   → due（每 5 分钟）                   命中 → 状态 ringing/delivered，打印文案
   → 宿主投递                           微信 / 其他渠道
   → 用户 ack（模型代调）                状态 acked，rev+1
   → 日切 rollover                      旧窗口进 history，生成新一天
```

排查顺序固定：**先看&#x20;**`status --json`**（状态对不对）→ 再看&#x20;**`hermes cron runs`**（触发有没有）→ 最后看投递日志（发出去了没）。**

这三步能把「代码没判断」「宿主没触发」「渠道没送到」彻底分开，不要一上来就怀疑模型。
