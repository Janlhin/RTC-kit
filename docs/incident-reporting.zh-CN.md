# 故障记录与上报

[English](incident-reporting.md)

本指南从本地错误开始，直至经人工批准提交的 GitHub issue（#68、#74 层 B），从而形成文档闭环。
它无法检测中断或修复调度程序。
外部中断检测仍为 #25。
一个失效的调度器无法通过同样已损坏的路径可靠地报告自身。

### 记录已知信息

保留 errors.md 中现有的“场景 -> 后果 -> 下次怎么做”追加式单句记录。
区分观察到的事实与假设。
仅记录实际获取的证据；将拟议的验证标记为“未执行”。
系统文件之间出现意外分歧时，仍应停止操作、记录信息并告知用户；在报告过程中不要修复这些文件。

虚构的本地示例（非所报告事件的复现）：

> 场景：临时测试工作区中的 due 返回退出码 1（已观察到） -> 后果：该次调用未产生任何提醒输出（已观察到；未检查投递情况） -> 下次怎么做：检查捕获到的错误；缺少模块只是一种假设，尚未得到验证。

一次调用失败并不能证明存在服务中断时长、投递遗漏或根本原因。
切勿编造模块名称。
首次发现的可能系统缺陷足以作为提出一个 GitHub issue 的理由；只有当类似情况第二次出现时，才需要另外提议制定一条固定规则。
这两项都需要在各自的外部/策略变更之前获得人工批准。

### 搜索、脱敏和准备

首先在该选定的仓库中搜索现有报告。
即使身份验证或网络访问失败，也应将本地草稿保存在运行时状态文件之外。
现有的报告可能需要回复，而不是创建重复的 GitHub issue；这两种操作都需要批准。

```powershell
gh issue list --repo <OWNER/REPO> --state all --search "<minimal symptom>"
```

准备一个全新的独立草稿文件，不要复制 errors.md。仅包含：

- 受影响的版本/提交记录以及一个经过最小化处理的干净环境。
- 观察到的行为与预期的行为。
- 已执行的确切验证及其结果；标明未执行的步骤。
- 明确标记为未验证的假设，以及接下来建议的检查项。
- 相关现有 issue链接及任何尚不确定的事项。

排除个人日程、用户名/地址、绝对本地路径、凭据、对话文本和不相关的日志。
在请求批准前，必须对所有拟分享的摘录做脱敏处理。
不要附加 errors.md 或完整状态文件。
如果无法安全地隐去必要证据，请询问用户转而使用哪个私密渠道。

### 获得批准后提交

向用户展示确切的目标仓库、标题、正文以及每个附件。
对某一草稿的批准，并不代表可以发布不同的文本、用于其他仓库或添加额外附件。
紧急人工通知与发布 issue 的权限是分开的。

以下命令仅可在获得批准后使用。
在文档验证期间切勿运行它。
用已审核的值替换占位符；正文文件只能包含已批准的脱敏草稿。
如果提交失败，请保留草稿并报告失败；不要无限次重试或阻塞调度。
如果结果不确定，请在重试前先进行搜索，以避免重复。

```powershell
gh issue create --repo <OWNER/REPO> --title "<approved title>" --body-file "<approved-draft.md>"
```

以下内容完全虚构，包括版本和搜索结果；这并非已完成的搜索或提交。

- 目标：`<OWNER/REPO>`
- 标题：`due 退出且未提供可操作的诊断（虚构示例）`
- 版本/提交：`<tested-commit>`（占位符，不是已核实的证据）
- 设置：使用合成提醒的临时工作区；不含个人数据。
- 现有 issue搜索：无匹配报告（虚构结果）。

建议正文：

> 观察到：在临时测试工作区中，一次 due 调用以 1 退出，且未产生任何提醒输出。
预期：成功完成判定，或给出可操作的诊断。
原因：未经验证；缺少模块仅为一种假设。
投递和中断时长：未检查。
下一步建议：检查一段经脱敏处理的错误摘录。
未附加原始工作区文件。

### 在不重写历史的情况下进行跟踪

提交确认后，在 errors.md 中追加一条简短的后续记录，包含该 GitHub issue 的 URL 和状态；保留之前的条目。
Issue 是一个跟踪项，而非已修复缺陷的证明。
只有在检查了相关提交记录和结果之后，才能将某项修复标记为已验证。
不得仅因上报失败而停止调度。
这不会覆盖针对不一致系统文件的现有“停止并报告”规则。

虚构的后续条目（仅在确认真实提交后追加）：

> 场景：已批准的报告已在 `<confirmed-issue-URL>` 提交 -> 后果：已跟踪，但未修复 -> 下次怎么做：等待问题分流处理，并验证任何拟议的更正。

经批准的摘录内容可以包含在正文中。上述 create 命令不会上传附件；任何单独获批的附件都必须通过已审核的渠道手动分享。回复现有 issue 也需要批准其确切的目的地和文本内容。
